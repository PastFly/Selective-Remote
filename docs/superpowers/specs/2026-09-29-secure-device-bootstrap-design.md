# Secure device bootstrap and approval — 0.32 design

## Intent and boundary

The Owner wants real, explicit device admission before any production Vault v2 CEK delivery. This change uses the merged dormant signed-certificate foundation and adds an account-scoped, fail-closed bootstrap and approval protocol across Mac, browser and Cloud. It does not enable Vault v2, change legacy Team Vault access, deploy Cloud, or introduce grants/groups/ACL. It leaves the separate registry and wrapper direct-SQL hardening gate intact.

## Audit of current identity

The existing Mac and browser device private keys are locally held P-256 ECDH keys for Team Vault wrapping. The server stores their public keys and enforces equality after registration, but the server also supplies the key and displayed fingerprint to an approver. `key_approved_at`, `account_key_approved`, `key_registered`, and Team `invitation_admitted` are server policy state, not an independently authenticated signing root. Password-derived Personal Vault wrapping is symmetric and unsuitable as a root because the authentication server receives the password. Remembered browser sessions and device keys do not establish a new client's trust in a server-supplied root. The merged PR #214 signing root is therefore required; the existing ECDH device key is reused as the certificate subject and for proof of possession.

## Root and bootstrap

The first device explicitly creates a local P-256 ECDSA account signing root after authenticated login and user confirmation. Mac stores the private scalar and account/endpoint pin in its protected Keychain envelope; browser stores a non-extractable signing key and pin in IndexedDB. The client signs its own v1 certificate and directory checkpoint, writes the pin locally before publishing the root, and sends only public root/certificate/checkpoint records to Cloud. The server serializes root creation on the account row and rejects an existing different root. If publication fails, the local root remains pinned and retry is idempotent. If another root appears, the client fails closed; it never adopts the server's root automatically. A new client receives the root fingerprint and initial trusted checkpoint digest through an authenticated out-of-band transfer from the root custodian; it verifies and pins them before accepting any server record. Browser site-data loss, a new profile or an unpaired Mac causes `PAIRING_REQUIRED`, never trust-on-first-server-response. Loss of every root custodian causes `RECOVERY_REQUIRED`; recovery or reset is a separately reviewed design and requires future Vault rekey.

## New-device admission

The authenticated new device reuses its existing local ECDH key and creates a pending request bound to account ID, device ID, exact canonical public key, fingerprint, platform, display name and expiry. One open request per device/key version is allowed. The server never marks a request approved merely because the legacy `key_approved_at` exists. The new device displays its key fingerprint and pairing instructions. The root custodian sees an actionable, deduplicated Notification Center item and opens a review view with device name, platform, creation time and key fingerprint. The person compares the fingerprint on both devices through a direct channel and explicitly confirms a match.

The custodian then starts a short-lived, one-use ECDH proof challenge: it generates a fresh ephemeral P-256 key and random nonce. Cloud relays public challenge material, bound to account/request/device/key digest, and serializes challenge state. The new device derives a shared secret with its registered private ECDH key and returns an HMAC-SHA-256 proof over a domain-separated canonical challenge transcript. The custodian derives the same secret and verifies the proof before signing a certificate. A challenge may be consumed exactly once, expires after five minutes and is invalidated on rejection, revocation or rekey. Neither the server nor an attacker with only the public key can forge the proof. The server may relay or suppress messages but cannot force a root signature. Cryptographic verification occurs on the trusted custodian, not the untrusted server.

After proof and user confirmation, the custodian signs a v1 certificate binding account, device, exact ECDH public key, key version, serial, issuance time and root fingerprint; it signs a strictly higher-version directory checkpoint containing the certificate digest. The server atomically publishes the signed records and marks the request approved under an account lock. The server verifies signatures and exact key equality as defense in depth. The new device accepts them only after out-of-band root pinning and local verification. A valid account certificate never implies Team membership, current epoch, Team admission or future wrapper capability.

## Rejection, revocation, rekey and concurrency

Rejecting a request records a terminal state and prevents later approval. Revoking a device removes it from a new signed directory, stops future v2 wrapper eligibility and preserves the historical certificate for audit. Old plaintext already received cannot be erased. Same-device-ID key changes fail closed at legacy registration and in the new request path; explicit rekey creates a higher key version and serial after revoking/superseding the old identity. The server serializes approval/reject/revoke/rekey and directory version allocation on the account root row; DB uniqueness prevents duplicate active request, serial, challenge and version. A stale signed checkpoint or concurrent transaction fails rather than overwriting newer state. Separate registry/wrapper SQL gates remain required before those production APIs.

The root custodian is the only approver in this first implementation. A Team Owner/Admin cannot act as universal account root; Team admission and membership epoch are separate. Multi-custodian transfer, root recovery and Team-specific policy are later reviewed steps.

## Verification and wrapper gate

The pure `isDeviceEligibleForV2Wrapper` decision requires a pinned root, valid signed certificate and latest known signed directory, established proof/approved request, no revocation, and, for Team scope, active membership, matching epoch, explicit device admission and capability. An absent or stale input denies. The production CEK path remains globally disabled until the rest of the 0.32 security/access stack is complete. The local high-water/digest blocks replay of older or forked checkpoints already seen. A malicious server can suppress a checkpoint never seen by a client; fresh witness or out-of-band re-pairing is required for stronger freshness. Browser XSS or compromised server-served JavaScript can bypass browser checks; browser trust must not be described as equivalent to native Mac.

## API, audit and notification

Account-authenticated, CSRF-protected endpoints support root publication/read, pending creation/list/read, challenge start/read/answer, approval/rejection, certificate/directory read, revocation and explicit rekey. Responses are account-scoped and return generic errors for foreign IDs. Mutations require idempotency keys, bounded bodies, expiry and account-row transactions. The server stores no private root or device keys. A separate account audit stream records `device.pending`, `device.approved`, `device.rejected`, `device.revoked`, `device.rekey_requested`, `device.rekey_approved` with IDs, time and non-secret version/fingerprint fragments only. Notification projections derive one actionable item per pending request and resolve it after source state changes; polling must not create duplicate items.

## Acceptance

Tests cover first bootstrap/restart/conflicting root; valid, duplicate, rejected and expired requests; exact fingerprint comparison; all certificate field mutations; valid, replayed, expired and wrong-device proof; substitution before and after approval; stale cert/directory and revoked device; cross-account and cross-Team access; explicit rekey; root loss and browser storage loss; notification dedupe/resolution; and concurrent approve/reject/revoke/rekey/challenge races on PostgreSQL 16. Mac and browser verify the same canonical signed fixture. Full Swift/Cloud suites, Release build, exact-head formal Codex Security scan, CI and Test DMG gate the PR. The PR stays unmerged for a fresh Owner exact-head decision.
