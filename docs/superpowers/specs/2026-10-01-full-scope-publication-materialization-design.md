## Product result and three PR boundaries

1. **Mapping and read/materialization:** persist exact legacy-to-resource identity, including Folder identity; introduce authenticated generation-bound reads; implement matching Mac/browser verification, unwrap, decrypt and local materialization. No active-generation policy/content mutation.
2. **Published mutation:** implement signed complete preview, client preparation of whole immutable generations, atomic policy/publication commit, stale/retry handling, key rotation and effective-delta notifications. No production enablement or deployment-controller cutover.
3. **Staging acceptance and rollback integration:** integrate the independent compatibility fence into the actual controller, deploy the reviewed candidate to test staging with protected backup, explicitly migrate synthetic test Vaults and prove real two-device/old-client/restart/concurrent workflows. Keep ordinary Vaults V1. Close only gates demonstrated by evidence.

These are dependency-ordered PRs, each with its own implementation plan and review. PR1 retains the old ACTIVE freeze. PR2 introduces a separate publication coordinator and does not weaken existing PREPARING-only store methods. PR3 provides runtime evidence. Fixture success alone never makes RC ready.

## 1. Exact identity, conversion and folders

The encrypted source is the exact authorized schema-1 export, not the UI's temporary record array. Inventory covers records, tombstones, vector clocks, modification times and all supported fields. Known Host, Credential, Snippet and Forwarding records map to their exact policy kind. Live path prefixes produce Folder resources, with an explicit canonical path algorithm identical on Mac/browser. Preserve path components byte-for-byte in encrypted data; do not merge distinct names through case folding or Unicode normalization. Reject ambiguous/invalid paths rather than assign a guessed parent.

For every source entry, persist a scope-bound source-key → resource-ID mapping before encryption. A source key distinguishes original record identity/type and, when necessary, duplicate ordinal; duplicate live valid IDs remain a typed blocker, not silently distinct resources. Reuse a valid canonical UUID only after global scope/collision checks. Otherwise assign and persist a UUID once. Folder identity uses the persisted exact parent/component map; rename/move changes attributes and edges, not the resource UUID. No registry ID is inferred from a displayed label, local record UUID, position or nearest path.

IDs belong permanently to their Team/Vault resource identity. A new generation references the same identity; it does not claim the ID through a competing migration attempt. Add a shared physical identity reservation and generation associations with scoped foreign keys. Existing attempt-owned reservations must be reconciled explicitly, including discarded attempts, before this contract is enabled. Cross-Team/Vault reuse and resurrecting a tombstoned ID are rejected. Deleting an identity leaves its tombstone; recreating a logical item receives a new ID. Direct SQL, create/discard/publication races and both registry/generation insertion orders must satisfy these rules.

The custodian's source mapping, source fingerprint and tombstone/clock preservation metadata are an encrypted, generation-bound administrative sidecar. It contains no duplicate live resource payload or SECRET; original live fields are preserved in their appropriate resource part. Only explicitly selected verified publishing custodian devices receive its key; holding Owner/Admin role alone does not grant it. It is not an ordinary recipient resource or a plaintext server index. Initial preparation may retain the existing legacy-key checkpoint locally, but later publication cannot depend on a retired whole-Vault key. Every recipient part also contains its own resource/scope/kind linkage, enabling an authorized local contextual action without access to the administrative sidecar. Do not distribute the legacy full export to a granular recipient.

Credential METADATA uses the existing explicit safe label/type/username whitelist; SECRET preserves the remaining original data. ViewMetadata never downloads, decrypts or caches SECRET. Credential.Edit without Reveal is invalid at write time and in the evaluator. Ordinary GENERAL parts expose only their approved non-secret payload. Unsupported `sshKey`, unknown kinds or Host/Forwarding embedded secrets remain typed whole-attempt blockers under the accepted converter; never silently drop or move secrets into View data. A representative supported release export must migrate without these blockers. A blocker in normal release-required data keeps RC blocked; it cannot be reported as successful full-scope acceptance.

Folder names/content are encrypted GENERAL parts. Container View maps through every live Folder level to Host.View, Credential.ViewMetadata, Snippet.View, Forwarding.View and descendant Folder.View. Reveal/Edit/ManageAccess/Create/Folder.Manage do not inherit. A directly entitled descendant need not gain ancestor access: render an opaque unavailable ancestor or a flat entry. Existing authorized payloads may already contain a legacy path; do not claim that withholding the Folder key erases that previously disclosed path. Broken, cyclic or cross-scope parents block publication.

## 2. Generation identity and recipient reads

A generation has an opaque ID, monotonic per-Vault sequence, previous manifest hash, exact Team/Vault scope, immutable graph/policy/crypto descriptors, source or operation commitment, trust/read-set commitment, and custodian root signature. The current pointer selects one complete generation. Sequence allocation and predecessor checks are server-CAS enforced; clients reject a lower sequence or a different hash at an already observed sequence. Preparation cannot expose a new current pointer.

Do not send the full administrative policy/trust snapshot or other recipients' wrappers to an ordinary reader. Define a versioned **signed public generation header** containing only scope, generation/sequence/predecessor, descriptor commitment and publisher identity/key epoch. Each immutable part descriptor binds resource/kind/part, registry/content version, parent, exact ciphertext hash, wrapper-set commitment and crypto context. Authenticate a reader's descriptor with a publisher root signature over that descriptor plus the signed-header hash. Use existing canonical JSON, domain-separated hash/signature and device-trust primitives; this is a bounded signed projection, not a second permission evaluator. Administrative manifest and per-part descriptors must be cross-validated before READY. Invalid, omitted, substituted or cross-generation descriptors fail closed.

Wrapper membership can be proven without returning another recipient's identity or wrapper: use a domain-separated SHA-256 Merkle commitment over canonically sorted wrapper descriptors. Leaf input includes full scope/context, recipient identity/epoch/device/key version and encrypted-wrapper digest. Parent hashes include a separate domain and left/right ordering; duplicate keys are invalid and an odd final node is paired with itself. Return only the subject's wrapper and bounded inclusion proof. The exact byte vectors, ordering and empty-set rejection must match Swift/browser/server tests. The signature authenticates the commitment; a proof alone is not trust or permission. Existing foundation generations lacking this reader projection are not exposed through the new endpoint; synthetic ones require an explicit compatible republish. Never pretend an unsigned server projection is equivalent to a signed manifest.

Publisher root/key authenticity requires an independently pinned **publisher account** root, verified certificate/directory and stored high-water. Existing device pairing is signed-in-account scoped and cannot establish another account's publisher trust. Add a bounded Team-scoped publisher identity bundle read, available only to current members and tied to the selected publication: exact publisher account/device/key epoch, public root, certificate and signed directory checkpoint. Do not expose a global account/device enumeration endpoint. Validate account/scope/certificate/key linkage before displaying verification.

For the signed-in account, reuse its verified endpoint/account pin. For another account, Mac/browser show an explicit “Verify publishing identity” step with the canonical root fingerprint and publisher identity. The user must compare that fingerprint through an independently obtained trusted channel (in-person fingerprint/QR comparison or an already verified custodian), then explicitly persist a pin scoped to endpoint/Team/publisher account. Copying a fingerprint from the same server page does not establish trust; no automatic TOFU, invitation-derived root trust, silent pin replacement or cross-account device approval. Verify the bundle against that pin and advance its directory high-water before verifying any publication signature. A later publisher/root change requires separate verification; mismatch stops decryption. This is a narrow publisher verification flow, not permission to sign another account's device certificates. Root recovery remains deferred; loss of publishing material is a typed blocker. Browser key storage/XSS and first-contact suppression limitations remain documented.

Add explicitly stage-gated authenticated routes under `/v1/teams/:teamID/vaults/:vaultID/publication`: current signed header, bounded authorized-resource directory, exact signed descriptor and exact ciphertext part. Every request checks active membership epoch, exact account/device admission, current verified device key/trust state, Vault ACTIVE/current-pointer coherence, and the single effective-policy evaluator for the requested part. Owner/Admin inspection authority does not automatically authorize SECRET delivery. Outsiders get the existing non-enumerating denial. Ordinary readers see only their entitled resource descriptors and their own wrappers; administrative groups/grants/audit directories retain the Owner/Admin role gate.

Pin generation ID/hash on every page/part request. A generation switch returns typed `publication_changed` and requires a new read; never splice parts across pointers. The cursor binds scope, actor account/device, generation and filter, has a bounded lifetime and requires a valid server signature. A restored old cursor cannot bypass fresh membership/revocation. Directory pages are at most 100 resources; exact resource lookup works off-page with the same authorization. Names/search text stay local after decryption. Reads emit no access-change notification.

At publication the custodian also signs a bounded per-recipient-device inventory commitment: header hash, exact account/device/membership epoch, authorized resource/part count and digest of its complete canonically sorted resource/part descriptor identities. It contains no other recipient's inventory. Directory pages identify this commitment; the client verifies the final count/digest before treating absence as authoritative deletion or replacing its coherent local directory. A valid descriptor proves that part, not completeness of a truncated response. Partial/withheld pages remain incomplete/UNKNOWN and cannot clear prior models as “revoked”. Server authorization still denies a revoked subject or a subject with no effective part permissions.

Revoked membership/device/permission is checked on each request. No shared unauthenticated ciphertext URL, legacy-wrapper fallback, server decryption or request-controlled activation flag. Cache headers prohibit shared caching. Downloaded ciphertext alone is not a YES usability assertion.

## 3. Mac/browser materialization and ordinary editing

Both clients use one transport/identity-bound pipeline: read header → verify pinned publisher/signature/high-water → fetch authorized descriptors/wrappers → verify commitments/context → unwrap with the exact admitted local key → authenticate/decrypt → validate kind/schema/resource linkage → stage local objects → recheck current pointer → atomically publish the local view and advance high-water. A current-pointer change, logout, account/endpoint/device switch, revocation, tamper or key failure prevents an old response from populating the new session.

High-water is persisted durably before a newer view becomes authoritative. Remembering a higher generation and losing local payload does not permit accepting a lower generation. Mac uses the existing device-local secure persistence; browser uses account/endpoint-bound storage and its existing nonextractable-key protection. Raw CEKs/plaintext exports never appear in logs, URL parameters, unprotected preferences or diagnostics. Network cancellation is supplemented by captured identity/generation checks at persistence and final display boundaries.

A successful entitled GENERAL/METADATA part becomes the corresponding scoped model and durable resource reference used by the real context-menu Share/Who-has sheet. Folder trees use only decryptable names. SECRET is retrieved separately only when policy and local verified wrapper/key allow it; Reveal/Edit controls remain disabled otherwise. New-device trust approval alone does not invent wrappers or complete synchronization.

`policyEffective` remains principal-scoped; `deviceUsability` and `effectiveUsable` are exact-device YES/NO/UNKNOWN. Server wrapper presence remains UNKNOWN. Only a successful locally verified unwrap/decrypt can show that device's YES for that exact part/generation; it never upgrades another device or a policy-only result. Missing/revoked key gives NO; a failed or incomplete query gives UNKNOWN.

Clients retain the prior coherent encrypted cache during preparation/temporary network failure and label it stale/offline, never “confirmed current”. After authoritative access loss, detach affected live models, close secret displays, cancel pending actions and remove managed cached keys/plaintext where possible. This is best-effort local cleanup: previously copied plaintext, exported data or keys cannot be revoked retrospectively. Old generations are not made available online as a recipient fallback after cutover.

Editing a published resource, move, grant/group change or delete uses PR2's publication flow. PR1 renders a useful publication-required/read-only state. There is no fallback to a V1 whole-Vault write or dormant registry mutation. Forwarding.Run/Host.Connect/Snippet.Run are not new ACL permissions; operational paths require whatever authorized resources/credential parts they actually use and never bypass unavailable secrets.

## 4. Signed preview and complete new generations

For ACTIVE changes, expose a distinct publication preview/start/upload/validate/commit/read-receipt coordinator. Existing PREPARING policy APIs remain unchanged. Preview is read-only: it evaluates the desired graph/policy using the same inheritance/masks/Team role ceiling, computes complete principal effective deltas and per-device crypto recipients, affected Vaults/resources, required keys, payload/wrapper counts and blockers. Group changes are Team-scoped and never acquire Vault ownership.

Bind the signed preview to actor account/session/device/key epoch, operation/idempotency ID, exact request, complete ordered Team read-set, predecessor pointer/hash for every participating Vault, desired policy hashes, count totals and expiry. Pagination must exhaust and match all counts before confirmation. Secret/session rotation or restart may invalidate it; return typed `preview_expired`/`preview_invalidated`, require a new preview and never accept unsigned/fallback commit. A changed request/selection/Team/Vault/recipient invalidates it immediately. Preparation may outlive preview, but commit always requires a fresh signed preview whose canonical request/read-set exactly matches the frozen generation; otherwise discard/reprepare.

The publishing custodian must have existing Owner/Admin mutation authority under Team policy **and** verified local keys for every required plaintext part and the administrative sidecar. ManageAccess and an Admin role do not manufacture key access. If no currently available authorized device can prepare the complete generation, return typed `publication_custodian_unavailable`; preserve the old publication and show a blocked operation. No server plaintext/key recovery. A new custodian requires the existing verified trust/key-transfer architecture, not an implicit grant.

For repair after a membership/device/trust change, introduce a separate stage-gated **predecessor repair read**, never an ordinary recipient fallback. Require a fresh signed repair preview bound to the surviving custodian account/device, current post-revocation Team read-set and exact predecessor pointer/hash. Recheck existing Owner/Admin ceiling, current membership/admission/certificate/root, and for each requested part the intersection of its predecessor entitlement and its entitlement evaluated against the current post-revocation state. Return only immutable predecessor ciphertext/descriptors and that same surviving device's still-valid old wrapper; never wrap for a newly admitted device, return another device's wrapper or bypass SECRET permission. The encrypted sidecar also requires that device's explicit predecessor custody entitlement. Recheck this scope/current read-set on every bounded repair page/part request. Do not require the obsolete full-Team snapshot to match for this narrowly reviewed route; current authorization and signed repair scope replace that check, without changing ordinary reads. Missing old wrapper/key, any removed entitlement, expired preview or a new revoke denies repair and returns a typed custodian/read-set blocker. This permits an authorized surviving device with keys but a lost ciphertext cache to rebuild; it cannot recover a lost key or create custody from a role.

Prepare a complete new immutable generation for each participating Vault, preserving resource UUIDs and all unchanged logical data. **Use fresh CEKs/nonces for every part of each new generation.** This simple conservative rule includes every part whose recipient access is lost and avoids CEK/context reuse across changed generation AAD; it costs full-Vault encryption and is deliberately chosen over partial-generation consistency. Wrappers cover exactly every current verified admitted device entitled to each part. Extra, missing, foreign, revoked, unverified or wrong-epoch devices block READY. New members/groups gain no decryptability before complete publication.

Checkpoint exact prepared bytes, stable identity map, source/read-set and completed objects durably on the custodian device before retry. Initial migration may use the locally held legacy-key checkpoint; fix-forward uses a fresh checkpoint key protected by the existing device-local secure envelope (Mac Keychain; browser nonextractable wrapping key), bound to account/endpoint/Team/operation/generation. Loss of that local protection blocks resume; it never sends plaintext to the server or borrows an old recipient key. Retry reuses only persisted immutable bytes. A missing checkpoint requires a new attempt/fresh keys, not re-encryption with an old CEK/nonce.

Round-trip verify all parts with the custodian's authorized local keys and verify exact wrapper commitments before signing. READY freezes identity associations, encrypted sidecar, graph, desired policy, signed header/descriptors, recipient commitments and object hashes. A changed byte conflicts; no in-place update to READY or ACTIVE ciphertext/wrappers/policy.

## 5. Team-wide consistency, concurrency and atomic commit

The existing ACTIVE reader binds complete Team memberships/groups/edges/device/trust/policy snapshots. **Do not remove this guard to allow an unrelated group write.** A policy/content operation affecting an ACTIVE Team prepares coherent successor generations for **every ACTIVE Vault in that Team**, even when one Vault's logical policy is unchanged. Commit switches them all atomically with the Team mutation. Current live READY attempts must be explicitly discarded before starting; otherwise return `publication_ready_attempt_exists`. V1 Vault content stays V1; legacy Team policy rules still apply. PREPARING contexts never authorize changing another published Vault through the old API.

Initial bounds: at most 10 ACTIVE Vaults and 1000 live resources including Folders across the atomic operation; at most 10,000 complete device wrappers; at most 64 MiB encrypted checkpoint and 128 MiB aggregate prepared ciphertext/sidecar. Check actual encoded bytes and fanout before encryption/upload and again in storage. At most 100 descriptors per page and 1 MiB encoded part/descriptor upload request. A single larger part or over-bound operation returns a typed limit with safe counts and no partial mutation. Do not split one Team publication silently into batches; larger Teams remain unsupported until a separately reviewed consistency protocol. UI may suggest a smaller independent operation only if it changes the actual affected Team read-set safely. Scale tests include boundary and boundary+1.

Use one deterministic transaction/lock order: Team, sorted participating Vaults, operation/attempts, identity reservations, then policy/group/member/device/trust tables. Preserve the existing direct-SQL-conflicting lock strategy and protect phantoms, membership/group epochs, trust/key changes, tombstones, identity uniqueness and current pointers. Under locks recompute the full canonical read-set, role ceiling, complete desired effective policy/recipient coverage, valid signed preview/expiry and READY commitments. Any stale input aborts **all** policy/pointer/audit/receipt changes. Retry serialization/deadlock only with the identical operation and bounded attempts; never automatically re-preview and broaden consent.

The transaction installs generation-linked policy versions and updates all participating current pointers/sequence/manifest hashes plus any Team group mutation, audit, notification outbox and idempotency receipt together. Reads observe the old committed set or the new committed set. An access request begun earlier may finish from its earlier authorized snapshot; no claim can revoke bytes already sent. New requests after COMMIT authorize only the new set. Old generation objects are retained privately for controlled recovery until a bounded operator retention policy removes them; ordinary recipients cannot fetch them.

Distinguish the **precondition read-set** used by preview/CAS from the **committed successor snapshot** authenticated by each new generation. Preview commits the exact requested mutation and deterministic expected next versions/epochs; generation signatures bind that expected successor state. Under locks, validate the old state, install those exact mutations/versions, then recompute and verify the successor snapshot before publishing pointers. A generation signed against the old policy/version must not become ACTIVE after a policy change. A revocation-repair preview starts from the already changed current state and signs its coherent successor.

Mutation of Team membership or device trust may need urgent revocation while a custodian is offline. Existing authenticated revoke remains allowed; it immediately invalidates delivery and makes the complete snapshot stale. Return/report `publication_repair_required`; never return a false successful granular publication. Restoring usable delivery requires a complete freshly previewed successor against the **post-revocation** state. New trust/admission similarly cannot invent a wrapper. Safety revocation may temporarily make the Team's published Vaults unavailable; show that state instead of bypassing the freeze.

Lost COMMIT response is resolved by account/device/scope-bound operation receipt and exact manifest read-back; identical replay returns the original result, changed replay conflicts. Disconnect after success cannot cause a second mutation or “failed” rollback. Client refresh failure preserves the receipt, blocks new writes and retries read only. Notifications are emitted via outbox only after committed **effective permission** changes: removing one path while equivalent permissions survive creates audit, not a false access-revoked notification. Crypto repair/key-availability status is distinct from policy change.

## 6. Migration, controller fence and rollback

V1 stays authoritative throughout initial preparation and failure/discard. A V1 write changes source revision/hash and invalidates the candidate. Activation commits complete policy/generation pointer, V2 format/schema and legacy retirement together; old whole-Vault APIs/code cannot return retired ciphertext/wrappers. No downgrade or automatic legacy fallback. Ordinary existing Vaults stay V1 through schema/runtime upgrades.

Before any test activation, the actual staging start/deploy controller must check the independent append-only compatibility fence retained outside DB backups/restores. Fence intent is durable before COMMIT; ambiguous COMMIT retains it. Record schema floor and the minimum committed generation/manifest for every activated Vault, extending it before later publication. Startup rejects old code/schema, missing fenced Vault, lower generation or hash mismatch. A restore of the DB alone cannot erase that independent evidence. Compatibility against pre-019 DB checks the schema floor **before** selecting nonexistent migration tables and returns a typed floor violation.

Fence records distinguish `PENDING_INTENT`, `CONFIRMED_COMMIT` and `PROVEN_ABORT`; all are append-only. A pending outcome stops guarded traffic until exact transaction receipt/manifest read-back resolves it. Confirmed COMMIT advances the minimum generation; a positively proven abort appends its resolution and preserves the prior committed minimum instead of requiring a never-published hash forever. Timeout, missing response or a restored older DB is not proof of abort. Never delete an ambiguous intent or infer failure solely from pointer absence.

After activation/published change, fix-forward only. No live DB restore to undo source rollout, no automatic fence deletion/reset or suppressing damaged fence. Restore tests use isolated databases and prove controller rejection before traffic. Restoring/bypassing both DB and fence is outside this protection. Client high-water detects observed rollback but first-contact suppression and arbitrary malicious-server rollback remain documented limitations; root recovery is not solved.
