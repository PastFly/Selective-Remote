# Safe Vault v1→v2 migration and publication foundation

## Authority and intent

Owner authorizes this architectural batch, its spec/plan and bounded implementation without micro-approval. Baseline is public main `60a9e80c294e139ffefab8332362be7bfff22800`. Produce a tested staging-only migration candidate and Draft PR, followed by a fresh exact-head Owner merge gate. Target release is 0.32.0. No production deployment/migration/activation, Access Manager UI, sharing rollout, Credential.Use, feed/tag/release or official signing/notarization.

## Architecture and alternatives

Use a persisted, immutable publication generation with a small atomic Vault pointer/format switch. Reuse existing AES-GCM/CEK/wrapper-v2 and signed device-directory primitives and the single Groups/Grants evaluator. Preparatory resources/parts/policy are private to the attempt; active publication views select only the exact Vault pointer. This avoids copying megabytes of ciphertext or thousands of wrappers during activation and gives one coherent read boundary.

Rejected alternatives: transitioning the live Vault to the old `V2_PREPARING` state closes its v1 API prematurely; bulk copying every prepared ciphertext into the old dormant tables makes activation proportional to payload/fanout. The new generation storage is an extension of the existing resource model, not an alternate permission evaluator. Future production reads/writes must use the generation/policy linkage; no production reader is enabled here.

## State and visibility

Attempt states: `V2_PREPARING → V2_READY → V2_ACTIVE`, with `FAILED_PRE_ACTIVATION` on an explicitly recorded preparation/validation failure. Retry of a failed attempt returns it to preparing after exact-source/snapshot checks. Discard is a terminal pre-activation marker with staging deletion. A Vault itself remains `V1_ACTIVE` throughout preparation, ready and failed states. `V2_ACTIVATING` is not durable: the activation transaction commits the attempt, publication pointer and Vault format atomically; readers see v1 or the complete v2 generation. There is no post-activation transition back to v1.

Preview is read-only and generates no IDs, audit event, progress or token side effect. It reports logical resource/folder/credential/snippet/forwarding counts, missing IDs, duplicate/colliding IDs, unknown records/fields, current recipient/key-custodian readiness, proposed grant/group readiness, required fresh CEKs, old-client impact, wrapper fanout and typed blockers. Server never receives decrypted legacy records; local conversion supplies a count/hash/opaque identity descriptor bound by the custodian-signed manifest.

## Exact conversion and identities

Client-only conversion accepts schema-1 `records` and `tombstones`. Support Host, Credential, Snippet, Forwarding; `sshKey` and unknown types are typed blockers until their exact conversion is designed. Every live logical record maps to exactly one resource, with separate generated Folder resources for each host/snippet path prefix. No silent drop or coercion. Preserve original data, vector clocks, modification times and tombstones inside encrypted parts/checkpoint. Host/Forwarding embedded password/private-key fields block migration rather than putting a secret into a View-only GENERAL part. Missing/invalid UUIDs receive an attempt-stable UUID; valid canonical UUIDs are reused only if unique and collision-free. Persist the source-key→ID mapping and source fingerprint before encryption; retry of the same source/attempt reuses it. Duplicate source IDs or cross-publication ID reuse fail closed. Folder path/name and source-key mapping remain encrypted client state; server sees only opaque graph, type and counts.

Credential has distinct `METADATA` and `SECRET` CEKs/ciphertexts. Metadata includes only an explicit safe label/type/username whitelist and the resource linkage; the secret part preserves remaining fields and original record. Unknown data fields remain in SECRET, never become metadata by inference. Reveal/Edit require SECRET; ViewMetadata needs only METADATA. Ordinary resources/folders use GENERAL. No Use without Reveal.

Prepare one immutable ciphertext per fresh part CEK. Persist the encrypted client checkpoint after each prepared resource, including stable IDs and completed encrypted objects/wrappers, under the existing locally held legacy Vault key. Retry uses completed bytes and never re-encrypts using an old CEK. A failure before a checkpoint can discard the new random CEK and generate a fresh one on retry. Checkpoint AAD binds Team/Vault/attempt/sourceRevision/sourceHash/snapshotHash. Plaintext and CEKs never leave the client; prepared ciphertext and wrappers are not logged. Resume requires the legacy key and exact checkpoint scope; loss/tamper is a typed blocker.

## Policy, trust and snapshot

The candidate includes a validated desired allow-only policy using the existing exact-kind masks, inheritance, Team group edges and epoch-bound direct grants. No candidate may create groups or mutate shared Team state. Default policy preserves legacy v1 disclosure for active members rather than silently removing recipients; restricted staged policies are explicit input and preview reports effective loss/widening. Owner/Admin authority and Admin target ceiling come from existing Team policy; ManageAccess does not independently authorize migration.

Capture a canonical, ordered repeatable-read snapshot: Vault source revision/key-generation/content hash/rotation state, Team policy revision, Vault policy version, existing registry and grant versions, memberships/roles/epochs, groups and their active edges, device identities/admissions/revocations, account root records and latest signed certificate/directory records, and existing crypto pointer/wrapper rotation state. Bind its SHA-256 plus desired-policy hash into every part context/manifest. All relevant changes before activation cause `migration_snapshot_stale`; reprepare with a new attempt is required, while an identical retry is idempotent. Actor must have active membership, existing Owner/Admin mutation authority, current-epoch explicit device admission, valid current signed certificate/public-key match, and schema-2 migration capability. Global key approval alone is insufficient.

Each entitled principal for a crypto part must have at least one current admitted device; every admitted eligible device for that permission requires an exact wrapper. Missing trust root/custodian, unverified certificate, removed/revoked member/device, missing eligible device or incomplete/extra/foreign wrapper is a blocker. Recipient devices must be independently verified by the client against supplied endpoint/account root pins and checkpoint high-water; trusting server root bytes alone is forbidden. A root-held ECDSA signature binds the canonical migration manifest; server validates it against the captured actor root. No crypto-usability claim follows from server validation: client round-trip verification of each part and the self-device wrapper precedes signing.

Root recovery remains an unsolved production gate. The enabled engine is restricted to an operator allowlist of disposable synthetic staging Vaults and an explicit staging environment; the staging harness holds known synthetic recovery material. This is not a root recovery implementation or proof for real Vaults. Real/production activation cannot be enabled by a request boolean or a client capability string.

## Staging storage and resume

Add checksum-tracked migration 019: scoped attempts, globally reserved migration resource IDs, immutable prepared part rows, manifest/hash/signature, encrypted checkpoint and progress markers. Foreign keys bind attempt/Team/Vault/resource. Only preparing attempts permit new object writes; exact replay returns the persisted object, changed replay conflicts. READY freezes identities, desired policy, object hashes and manifest. No public route reads staging objects. All staging store methods enforce actor scope and the explicit staging allowlist. Readers use joined active-publication views/internal loader only when Vault format and active attempt agree. Resource/part/policy versions are linked to that same manifest.

Failure injection covers registry/folder checkpointing, ciphertext, wrapper, manifest, validation, pre-activation and every activation mutation. Before activation, v1 remains authoritative and writable; a subsequent v1 write invalidates the candidate snapshot. Discard deletes only that attempt's staging, preserves legacy data and reusable Team groups, and writes a plaintext-free audit event. Different active attempts conflict. Lost COMMIT response is resolved by exact attempt/manifest read-back; activation replay of the same manifest returns success, a different one fails.

## Activation, concurrency and rollback

Activation locks the Vault/attempt and then the relevant policy/device/trust read set using a documented deterministic order and transaction table locks, protecting against direct-SQL writers and phantoms as well as API writers. Recompute the complete snapshot and verify READY manifest/object/recipient commitments under those locks. Prepared rows are already immutable; transaction updates only attempt status, active publication pointer/format/schema/policy linkage, privacy-safe audit and legacy retirement. Table count is fixed; activation payload work is bounded and independent of ciphertext byte size. Measure the remaining read-set cost at 100/1000 resources and multiple groups/devices.

The same commit sets `V2_ACTIVE`, clears legacy whole-Vault payload fields and removes legacy revision, current/old wrapper and invitation-wrapper rows. A schema guard prohibits format downgrade and reintroducing v1 payload/wrappers. Old code reading the current database can no longer return the original v1 ciphertext, including code that ignores format_state. Current legacy APIs return a safe upgrade-required error for authorized members, preserve non-enumeration for outsiders, and never fall back based on version strings. The internal v2 loader requires exact schema/capability and current membership/admission/trust plus effective part permission.

Restoring an entire pre-activation database removes database-local markers. No database-local trigger can protect against restoration of itself. The staging operator flow therefore requires an independent append-only deployment compatibility fence before activation, retained outside DB backup/restore. Its intent is durable before COMMIT; an ambiguous activation keeps the fence and requires recovery/retry. A compatibility check rejects code/schema below floor 19 and a restored DB missing a fenced Vault's active manifest. Production rollout remains blocked until this independent fence is integrated and recovery-tested in the real deployment controller. Bypassing the operator fence or restoring both DB and fence is outside this protection; do not claim malicious-server or arbitrary full-stack rollback resistance.

Before activation, discard is safe. After activation, fix-forward/recovery only; no automatic downgrade, legacy route fallback or automatic restore of retired whole-Vault data. Staging tooling provides preview/prepare/validate/discard/activate and compatibility-check operations with explicit environment/allowlist guards. It does not connect to or alter production by default.

Preview creates no audit/notification. No plaintext/keys/checkpoint contents in logs.
