# Access & Sharing: crypto and enforcement options

Status: design proposal, 2026-09-29. No schema, server or client crypto change is implemented. Current Team Vault is one client-decrypted AES-GCM document with a device wrapper for the entire Vault key (`cloud/public/team-vault-crypto.js:323-380,451-492`). A server ACL on record IDs cannot undo plaintext access through that key.

## Options compared

The labels describe a *future* ACL-capable format, not present behavior. `E2EE=YES` means the Selective Remote server does not receive resource plaintext or data keys. No option can erase plaintext already acquired by a malicious or offline endpoint.

`RECOMMENDED_ARCHITECTURE=E`: a v2 ACL-capable Vault is a **container**, not a universal content key. Each Host, Credential, Snippet and Forwarding resource has a client-generated content encryption key (CEK) and independently authenticated ciphertext. Client-generated CEK wraps go to approved member devices or a flat-group key. The server sees opaque resource identity/type, Vault and Folder parent IDs, grant edges, policy/key version and ciphertext metadata; it checks policy on every list, read, write, grant and wrapper fetch. It never receives E2EE plaintext or CEKs. Folder grants expand to descendant resource access but do not turn a path string into authority. An authorized key custodian client must create or rotate wraps and ciphertext; management permission alone never makes a key appear.

For an ordinary v2 direct/group grant, policy change and required wraps are staged and committed together with a policy-version check. Revocation first stops new server access and wrappers, then rotates CEKs/ciphertext for affected future versions before marking `rotation_complete`; resources with pending or inconsistent crypto state fail closed for new protected operations. A group key reduces per-member wrap fanout but its removal requires rekeying every affected resource CEK; rewrapping an unchanged CEK is insufficient after a former member learned that CEK. Content already copied remains beyond revocation. The design must bound rekey batch size and preserve at least one eligible custodian.

## Credential.Use without Reveal: seven mechanisms

Terms: `UI_HIDDEN` hides a control only; `NOT_EXPORTABLE` prevents normal key export but not all uses; `CLIENT_VISIBLE` means plaintext/key material reaches ordinary app memory; `BROKERED` means another trusted component performs an operation; `EPHEMERAL` expires at the target; `CRYPTOGRAPHICALLY_ISOLATED` means an unauthorized recipient lacks the CEK. None implies safety on a fully compromised device.

Current Mac AskPass stages a secret in a mode-0600 file and passes its path to a child process (`Sources/SelectiveRemote/SSHService.swift:1221-1235,1288-1302`); this protects against other OS users, not the authorized same-user process or malware. Current browser decryption returns a plaintext object (`cloud/public/team-vault-crypto.js:451-492`). A WebCrypto non-extractable key can still decrypt and return plaintext to script; `extractable=false` controls key export, not the confidentiality of the decrypted record ([W3C Web Cryptography Level 2](https://www.w3.org/TR/WebCryptoAPI/)). Apple's Secure Enclave can keep supported private keys out of app plaintext, but does not turn arbitrary SSH/RDP passwords into non-exportable operations ([Apple Secure Enclave guidance](https://developer.apple.com/documentation/Security/protecting-keys-with-the-secure-enclave)). OpenSSH certificates can constrain principals, options and validity when target servers trust a CA; they are a target integration, not a generic password substitute ([OpenSSH ssh-keygen](https://man.openbsd.org/ssh-keygen), [sshd_config](https://man.openbsd.org/sshd_config)).

`CREDENTIAL_USE_WITHOUT_REVEAL_GUARANTEE=NONE_IN_CURRENT_ARCHITECTURE`. V1 E2EE can give `CRYPTOGRAPHICALLY_ISOLATED` **Reveal** only to recipients with the credential CEK. It cannot give Use without Reveal to the same client if that client receives plaintext or CEK. For future use, prefer target-issued short-lived SSH certificates or hardware-backed signing where supported, followed by a narrow operation-bound broker for reusable passwords only with explicit Owner acceptance that this secret leaves the current E2EE boundary. Do not enable the prototype's Use checkbox or claim `NOT_EXPORTABLE` from a hidden field, software Keychain or WebCrypto flag alone.
