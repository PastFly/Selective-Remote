# Официальный macOS-релиз и канал обновлений

## Текущее состояние

Готовится кандидат **0.32.0 (163)**. Публичная загрузка и `Resources/updates.json` остаются на **v0.31.0 (162)** до успешной проверки официального опубликованного DMG. Метаданные 0.32 находятся в `Resources/updates.candidate.json`.

Test DMG использует режим `community` и временную ad-hoc подпись. Успешные CI, checksum и запуск такого DMG не подтверждают Developer ID, notarization или готовность официального релиза. `Release DMG` прекращает работу при отсутствии Apple-конфигурации; перехода на ad-hoc в этом процессе нет.

## Подготовка кандидата без публикации

1. Зафиксируйте окончательный commit/tree кандидата и результаты его обязательных проверок. Не переносите результаты старого кандидата на изменённый код.
2. Согласуйте `VERSION` и `BUILD_NUMBER` в `scripts/build_app.sh` с `Resources/updates.candidate.json`. Публичный `Resources/updates.json` заранее не меняйте.
3. Подготовьте RU/EN в `releases/0.32.0-notes.md`: для 0.32 именно его разделы `FINAL_DETAILED_RELEASE_NOTES_RU` и `FINAL_DETAILED_RELEASE_NOTES_EN` читает `scripts/release_notes.py`. Для других версий используется соответствующий раздел `CHANGELOG.md`. Согласуйте короткий текст README/сайта с теми же подтверждёнными возможностями и ограничениями.
4. Завершите реальную приёмку Cloud, миграции и чтения на втором устройстве в разрешённой тестовой области. Не выдавайте test-only V2 за включение для обычных Vaults. Сохраняйте незавершённые ручные и security-проверки в отчёте кандидата.
5. После настройки Apple можно собрать отдельный официальный кандидат через `scripts/build_app.sh` в режиме `official`, с точными identity, Team ID и notary profile. Сам скрипт сборки не публикует GitHub Release и не меняет feed. Проверьте подписанный кандидат, чистую установку, Gatekeeper, обновление с опубликованной 0.31, сохранение данных и откат. Не используйте для проверки основной профиль с личными данными.

Не запускайте `Release DMG` для предварительной сборки: этот workflow публикует артефакт, обновляет публичную ветку `main` и запускает объявление в Telegram.

## Apple-конфигурация

Нужны действующий сертификат **Developer ID Application** с его приватным ключом, точный Apple Team ID и доступ к notarization. Наличие аккаунта или файла сертификата без приватного ключа не подтверждает готовность подписи.

В GitHub **Settings → Secrets and variables → Actions** должны быть настроены переменные:

- `APPLE_TEAM_ID` — точный десятисимвольный Team ID;
- `DEVELOPER_ID_APPLICATION_IDENTITY` — точное имя `Developer ID Application: … (TEAMID)`.

И секреты:

- `DEVELOPER_ID_APPLICATION_P12_BASE64` — сертификат с приватным ключом в P12;
- `DEVELOPER_ID_APPLICATION_P12_PASSWORD` — пароль P12;
- `APPLE_API_KEY_P8_BASE64` — ключ API notarization;
- `APPLE_API_KEY_ID` — идентификатор ключа;
- `APPLE_API_ISSUER_ID` — идентификатор издателя.

Вносите значения только через защищённую конфигурацию Apple/GitHub/Keychain. Не отправляйте их в чат, исходный код или журналы. Проверка наличия имён конфигурации ещё не доказывает, что сертификат и API-ключ действительны; это устанавливается подписанием и notarization реального кандидата.

## Единственное финальное разрешение Owner

Перед публичными действиями предъявите точные PR/head/tree, итоговые проверки, подписанный кандидат и план production-развёртывания с откатом. Запрос должен явно перечислять требуемые действия: изменение `main`, production-развёртывание и допустимую область миграции/активации, создание неизменяемого тега, публикацию GitHub Release, последующее обновление публичного feed/сайта/README и автоматическое объявление в Telegram. Подготовка кандидата сама по себе такого разрешения не даёт. Любое изменение согласованного кандидата требует повторного согласования затронутого действия.

Публикация macOS-релиза не развёртывает Cloud: production выполняется по отдельно подготовленному и включённому в то же финальное разрешение плану. Не объединяйте это с включением V2 для обычных Vaults, если такая область не проверена и не согласована.

## Порядок официальной публикации после разрешения

1. Проверьте неизменность согласованного кандидата и его проверок. Создайте новый тег `v0.32.0` на точном согласованном commit после разрешённого включения изменений в `main`. Не перемещайте опубликованные теги и не перезаписывайте выпущенный DMG.
2. Запустите **Actions → Release DMG** для существующего тега. Workflow проверяет совпадение тега, исходного commit, версии, build и candidate manifest, затем наличие обязательной Apple-конфигурации.
3. Сборка подписывает вложенные компоненты и приложение, включает Hardened Runtime, подписывает DMG, проходит notarization, stapling и Gatekeeper и рассчитывает SHA-256 готовых байтов.
4. Workflow создаёт draft Release, загружает DMG и checksum, проверяет GitHub assets и публикует Release как Latest.
5. Он повторно скачивает опубликованный DMG, сверяет checksum и GitHub digest, проверяет Developer ID Application, точный Team ID, подпись, stapling и Gatekeeper. Та же проверка выполняется при повторном запуске для уже опубликованного Release.
6. Только после этой проверки workflow переносит candidate manifest в публичный `Resources/updates.json` отдельным non-force commit/push в `main`. Если `main` ушёл вперёд относительно тега, он останавливается без обновления feed. Не обходите этот барьер принудительным push или ручной подменой manifest.
7. После успешного обновления feed автоматически выполняется `announce-telegram`. Этот внешний анонс должен быть явно включён в финальное разрешение. Если он не разрешён, существующий workflow запускать нельзя до согласования способа выпуска без отправки объявления.

После публикации проверьте реальные RU/EN ссылки загрузки, версию feed и доступность артефакта. Обозначение «текущий релиз 0.32» и инструкции обычной установки допустимы только после подтверждения официального DMG. До этого сайт и README сохраняют v0.31.0 и явно называют 0.32 кандидатом.

Реализация: `.github/workflows/release.yml`, `scripts/official_release_preflight.mjs`, `scripts/run_official_release.mjs`, `scripts/official_release_publication.mjs`, `scripts/verify_official_release_asset.sh`. Они имеют приоритет над историческими описаниями порядка выпуска.
